# 调用接口与数据格式草案

更新日期：2026-11-17。

本文以“孩子出生后首次取名”和“Cultiway 法术命名”检验调用协议，明确类型注册、输入、输出、内容与保存的边界。产品行为见[设计讨论](设计讨论.md)，模块职责见[架构草案](架构与执行流程草案.md)，规则节点和字段覆盖见[规则与数据模型草案](规则与数据模型草案.md)。

生命周期与文化、语言的默认来源已经确认。本文中的接口名称、字段名、状态表示及版本数字仍是候选方案；JSON 用于评审数据形状，尚未实现为可运行 API 或正式包格式。

## 对外只保留少量入口

建议模组使用类型注册和统一生成入口。以下为签名示意，具体类型定义在实现时落实：

```csharp
public interface INamingRegistry
{
    RegistrationResult RegisterType(NamingTypeDefinition definition);
    RegistrationResult RegisterWordRole(WordRoleDefinition definition);
    RegistrationResult RegisterCondition(ConditionDefinition definition);
    RegistrationResult RegisterPartOperation(PartOperationDefinition definition);
    RegistrationResult RegisterCandidateProvider(CandidateProviderDefinition definition);
}

public interface INamingService
{
    NamingResult Generate(NamingRequest request);
}
```

注册定义包含稳定标识、所属模组、显示信息和参数声明。条件、部件与动态候选只在需要时扩展，普通类型只需声明输入、规则绑定、预览样例和校验。重复标识需要明确报错，不根据加载顺序悄悄覆盖。

`Generate` 负责验证请求、解析配置和调用执行器，始终返回结果，不直接写回对象。是否需要首次命名、保留原名、复制命名状态或执行事件改名，由接入方按生命周期决定；公共入口不提供绕过玩家名字保护的全局强制改名开关。

预览服务解析当前草稿与示例输入，再使用相同执行器。它不需要另一套生成算法，也不会调用真实对象的姓氏初始化或结果提交。类型、条件和部件声明是编辑器生成控件的依据。

## 六类数据分别处理

| 数据 | 包含什么 | 生命周期 |
| --- | --- | --- |
| 注册定义 | 类型、输入字段、词汇用途、条件、部件和校验能力。 | 模组注册期间可用；世界数据通过标识引用。 |
| 包内容 | 默认规则、词库、基础方案、补充操作与预设。 | 全局安装，按世界配置参与解析。 |
| 世界与对象状态 | 启用包、绑定、玩家覆盖、语言稳定偏好、名字和姓氏等组成部分。 | 随对应世界和对象保存。 |
| 有效配置 | 一次解析得到的规则、词库、覆盖与来源。 | 可缓存，由相关配置或内容版本变化使其失效。 |
| 命名请求 | 配置来源、种子、类型声明的输入和确定部件。 | 本次生成只读，不保存 Actor 或模组实体引用。 |
| 执行结果 | 成功与否、名字、部件、方案来源与诊断。 | 接入方决定提交哪些内容，失败不写半成品。 |

原版 `MetaType` 仅在适配层映射到命名类型标识。框架执行器与公开数据模型不要求游戏对象或 Unity 窗口类型。

## 输入必须有声明

建议输入支持文本、布尔、整数、数值、可选项，以及有声明元素类型的列表和记录。记录的字段也需要声明，避免把任意 C# 对象、反射字段或 `object` 字典作为扩展协议。

| 类型声明 | 可以怎样使用 |
| --- | --- |
| 可选项 | 性别、元素、法术形态等；传稳定值，界面显示本地化名称。 |
| 整数或数值 | 等级、境界序号、强度等；类型可声明范围。 |
| 文本 | 已有对象名、轨迹标识等只读信息。 |
| 列表与记录 | 一组带标识、层级、标签的法术修饰，或其他模组的结构化信息副本。 |

类型声明可以区分必需输入与可选输入。所有方案都必需的信息缺失或类型不符，返回请求错误；只被某些规则使用的可选输入缺失时，按已有的“条件不可求值／必需部件失败”规则跳过对应路径，继续尝试其他规则或默认方案。不能因为某条特殊规则需要信息，就把它错误地设为全类型必需。

例如，世界名不要求 Actor，普通动物不要求父母与文化，法术不要求个人姓氏。类型内输入名称和规则内部件名称可以是局部标识；跨类型引用的类型、词汇用途和扩展操作使用带命名空间的稳定标识。

## 请求与结果

建议请求包含以下信息：

| 字段 | 含义 |
| --- | --- |
| `name_type` | 已注册的命名类型标识。 |
| `trigger` | 首次命名、重铸、归属变化等场景；只表达本次原因，不代替接入方的改名判断。 |
| `configuration` | 当前世界配置和已选定的文化、语言引用；缺少文化或语言时分别采用适用的世界默认方案。 |
| `seed` | 本次生成的独立种子，不消耗游戏其他随机流程的状态。 |
| `inputs` | 与类型声明一致的只读字段值。 |
| `fixed_parts` | 已确定的姓氏等信息，普通取词与变换不能隐式重取或改写。 |

引用使用稳定值，不使用当前显示名称查找对象。请求中的文化、语言已经由接入按默认来源规则选定，生成器不自行遍历亲代、作者或国家重新猜来源。

结果建议区分三种状态：

| 状态 | 含义与接入处理 |
| --- | --- |
| `success` | 得到有效名字与部件，可以提交；标明采用文化方案还是类型默认方案。 |
| `unavailable` | 未注册类型、依赖缺失或规则与默认方案均无法生成等；提供原因，交给接入方最终回退。 |
| `invalid_request` | 输入不符合类型声明或请求结构无效；保留具体字段位置，不把错误文字当名字。 |

失败诊断应有稳定原因码、可读说明和对应类型、规则或部件位置。预览可以展开详细来源；实际生成不要求把完整追踪保存到每个对象。重试、嵌套部件和类型默认方案共享受限的执行预算，接入回退需要防止重复进入同一补丁。

## 案例一：孩子出生与首次取名

### 出生时只确定姓氏

假设孩子出生时属于河谷文化，该文化优先父姓，父亲已有姓“李”。出生接入取得亲代关系与出生文化，继承流程确定孩子姓氏并保存。若父亲使用姓氏但尚未取姓，先初始化并保存父亲姓氏；不为取姓而递归生成完整姓名。

个人姓氏状态的候选存储形状如下：

```json
{
  "schema_version": 1,
  "family_name": {
    "state": "assigned",
    "text": "李",
    "origin": {
      "kind": "inherited",
      "parent": "unit:401",
      "birth_culture": "culture:21"
    }
  }
}
```

`assigned`、`uninitialized`、`not_used` 分别表示已有确定姓氏、尚未初始化和明确不使用姓氏，具体枚举名称待定。原样保存的是完整姓氏，不根据姓名文字推断；亲代和文化引用只用于说明来源，读出姓氏不依赖来源对象仍然存在。

### 首次需要完整姓名

之后首次调用个人姓名入口时，复用已保存的姓氏，并选取该次命名适用的文化、语言和物种信息。请求示例：

```json
{
  "name_type": "worldbox:unit",
  "trigger": "initial_name",
  "configuration": {
    "world": "world:demo",
    "culture": "culture:21",
    "language": "language:7"
  },
  "seed": 739128,
  "inputs": {
    "species": "human",
    "sex": "male",
    "uses_surname": true
  },
  "fixed_parts": {
    "family_name": {
      "text": "李"
    }
  }
}
```

文化结构选择双字名规则，语言提供名字用字，执行器返回候选结果：

```json
{
  "status": "success",
  "text": "李青川",
  "rule": "base:person.two_given_chars",
  "plan_source": "culture",
  "parts": {
    "surname": {
      "text": "李",
      "fixed_part": "family_name"
    },
    "given_1": {
      "text": "青",
      "word": "base:given.qing"
    },
    "given_2": {
      "text": "川",
      "word": "base:given.chuan"
    }
  },
  "order": ["surname", "given_1", "given_2"],
  "diagnostics": []
}
```

接入在成功后保存完整姓名、自动或手改来源标记，以及需要保留的组成部分。已有姓氏的独立状态不被结果覆盖为另一个随机值。克隆时复制姓名、姓氏与组成部分；亡灵转换与升格按已确认的保留行为处理。

如果姓名取词失败，保留已经确定的姓氏，按既定顺序尝试默认方案和接入回退。以后读取名字直接返回已保存结果，文化、语言或包切换不重新命名。

这里的示例引用与词条标识只说明协议，不指向当前世界的真实对象，也不是对现有 TXT 内容的迁移约定。

## 案例二：Cultiway 法术命名

### 注册与准备输入

Cultiway 注册 `cultiway:spell` 类型，声明元素、形态、轨迹和修饰信息，并提供显示名称、预览样例、需要的词汇用途与校验。可以按需注册自定义候选提供器或部件，普通结构仍由文化规则编辑。

当前 [SkillNamingContext.cs](../../../Cultiway/Source/Core/AIGCLib/SkillNamingContext.cs) 已组织元素、形态、运动语义、轨迹和修饰；[SkillRuleNameComposer.cs](../../../Cultiway/Source/Core/AIGCLib/SkillRuleNameComposer.cs) 从技能实体构建这些信息。接入建议复用其领域解释，把结果转换为已声明的值或结构化副本，不把技能实体直接传入框架。

假设一门法术具有火属性、剑形态和燃烧修饰，调用示例：

```json
{
  "name_type": "cultiway:spell",
  "trigger": "initial_name",
  "configuration": {
    "world": "world:demo",
    "culture": "culture:21",
    "language": "language:7"
  },
  "seed": 85142,
  "inputs": {
    "element": "fire",
    "form": "sword",
    "trajectory": "linear",
    "modifiers": [
      {
        "id": "burning",
        "value_tier": 2,
        "tags": ["fire", "damage_over_time"]
      }
    ]
  },
  "fixed_parts": {}
}
```

这些值是候选输入协议示例，不要求 Cultiway 当前字段和语义资产按上述字符串重命名；实际映射由 Cultiway 的适配负责。

### 生成与写回

文化规则可以使用“元素修饰 → 形态词 → 术法后缀”，语言分别提供对应词库，得到“炎刃诀”一类名字。结果仍使用相同的成功状态、文本、局部部件标识、词条来源和输出顺序，交给 Cultiway 写回法术对象。

需要复杂评分时，模组可以提供带稳定标识、文字、权重和标签的候选，或实现已声明的条件和部件。按词汇用途取词仍经过统一筛选与抽取，使语言偏好、排除和来源追踪生效。核心不内置元素、修行境界或 Cultiway 的技能实体规则。

类型默认方案仍失败时，返回 `unavailable`，Cultiway 使用自己提供的最终回退，并保留失败原因。需要异步准备语义或候选时，由模组先完成准备再调用；本次执行读取稳定输入，不在生成期间隐式写对象或发起外部生成请求。

预览使用同一类型的模拟输入，玩家不必先在世界里创建一门真实法术。复杂列表与记录按声明提供通用控件，具体编辑形式与可选专用控件继续结合编辑器细化。

## 命名包文件边界

建议用清单声明内容入口和能力依赖，规则节点继续采用模型草案，不在本页重复定义另一套格式。例如：

```json
{
  "schema_version": 1,
  "id": "base:chinese_names",
  "version": "1.0.0",
  "name": "中式基础",
  "requires": {
    "framework_api": 1,
    "name_types": ["worldbox:unit"],
    "packs": []
  },
  "content": {
    "rule_schemes": ["rules/person.json"],
    "lexicon_schemes": ["lexicons/common.json"]
  }
}
```

包清单、规则、词库与方案用稳定标识相互引用；显示名称和文件路径不能承担持久化身份。清单路径只是候选文件组织示例，不表示仓库已生成这些资源。

已确认缺少可选模组时仅相关内容不可用，其他内容继续，玩家修改保留。按独立内容单元隔离依赖、保留启用边界及处理依赖循环的技术建议见[规则模型的依赖章节](规则与数据模型草案.md#依赖与版本)，精确 JSON 写法及校验算法在实施计划阶段 0 定稿。

## 保存什么，不保存什么

| 位置 | 保存的内容 |
| --- | --- |
| 全局内容目录 | 安装的包清单、词库、规则及预设。 |
| 世界命名设置 | 启用包及优先级、默认绑定、文化与语言选择、字段覆盖、新增内容和语言稳定偏好。 |
| 对象命名状态 | 完整名字、自动或玩家编辑标记、已确定姓氏和需要保留的组成部分。 |
| 草稿记录 | 对应世界与目标、基于的生效配置版本、未应用编辑；具体保存交互仍按编辑器草案评审。 |

有效配置、执行缓存和完整诊断树不作为世界对旧包内容的冻结。包卸载、扩展缺失或来源规则删除时，已有文本及稳定部件依然可读取；相关配置与覆盖记录原样保留并标记缺失。

建议分别标记包数据格式版本、公开 API 版本和世界命名数据版本，不拿包作者的内容版本代替结构版本。首次结构版本只服务于新框架自己的数据，不扩大到此前暂缓的旧存档或旧格式迁移。

## 两条流程共同给出的约束

两种对象都只需要“类型、配置来源、声明输入、种子与确定部件”这一类请求，以及统一结果。姓氏继承属于出生与长期状态流程，法术语义属于 Cultiway 的领域适配；两者都无需让生成器认识实际游戏对象。

下列内容还需要在接口定稿时落实：声明字段和结构化值的最终 C# 表示、操作与候选注册的参数协议、重试与嵌套的统一上限、包依赖及版本写法、诊断码与保存布局。多源词库权重、重复内容、列表操作与冲突处理已有集中于规则模型的候选方案，继续评审后再落实，不能仅凭这两个调用例子就视为已经实现。

本文是数据与职责的书面走查。具体接口收敛、核心验证、原版适配及跨模组接入按[分阶段重构计划](分阶段重构计划.md)推进，各自记录完成证据。
