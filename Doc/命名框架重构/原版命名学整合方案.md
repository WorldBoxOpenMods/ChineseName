# 原版命名学整合方案

2026-11-18。本文定义下一版的目标和验收条件。已运行的版本见[实现与验证](实现与验证.md)。

## 玩家如何编辑

单位和城市的部件编辑、语言对照、不同语系的中文写法和原版卡片使用同一张命名学页面。[命名学页内设计](命名学页内设计.md)

文化档案里的「命名学」是该文化命名规则的主入口。原有的单位、家族、氏族、城市、国家继续按类型查看。其他适用的原版类型和已注册的模组类型放入同一个类型选择器。保留原版卡片规则的编辑方式，并在同一页提供中文规则编辑。全局「命名管理」负责选文化、配置世界默认值和管理命名包，从那里打开文化规则也进入同一个编辑器。

编辑者可以改组成、顺序、条件、命名部件的词库用途，以及适用类型的姓氏继承。预览默认使用当前文化和选中的单位或城市所用的语言，也可以手动选另一种语言并排比较。预览标出每段文字的实际来源，包括语言词库、文化固定词和继承部件。草稿、应用与重置共用一套行为。重置指定字段后，该字段恢复随当前方案变化。

语言档案增加「命名词库」入口，展示各用途的词库、继承来源、分化产生的偏好和玩家修改。文化预览里可直接跳到当前语言对应的用途。命名包提供可分发的默认内容，文化和语言各自绑定游戏中的对象。

## 原版规则怎么融入

每个文化的每种命名类型只有一份生效的命名学，生成和预览都从这里解析。中文名默认规则使用现有框架的结构化部件。原版已经存在的规则可以继续按卡片运行，并在命名学里给某一组绑定语言词库用途。例如城市规则中的第一个词组绑定「地名用字」，另一个组保留文化自己维护的「城、府、关」。玩家通过原版的卡片顺序和词组编辑就能改变后续产出的名字。同一份规则可以同时使用两种来源。

| 内容 | 归属与读取方式 |
| --- | --- |
| 原版卡片顺序、条件、分支及组内固定词 | 由原版 `OnomasticsData` 保存。适配器按当前文化和类型读取，沿用原版卡片语义。 |
| 原版组的词库用途 | 中文名按文化、类型和原版组 ID 保存绑定。每组可用文化固定词或当前语言的词库。绑定词库缺失时以该组保留的词作回退，并在预览显示实际来源。 |
| 中文规则、适合中文的演化变体、姓氏继承 | 中文名保存相应规则引用和局部覆盖。规则正文以当前命名包为基础，精确到稳定的类型、规则和部件 ID。 |
| 语言词库及演化结果 | 中文名按游戏语言对象和词库用途保存绑定、自动差异与玩家覆盖。不同文化可复用同一语言词库。 |

新世界按包和物种采用默认规则。每个类型可在该页明确选择使用原版卡片或中文规则。编辑卡片时，原版控件操作草稿，应用时才提交卡片、词组和绑定。原版卡片和组仍能作为该类型的恢复选项。读取旧世界时，每个已有类型保留原来的有效来源，具体迁移见下文。

原版卡片可表示一组词、条件、分隔等规则，短模板按单字符卡片 ID 和固定组格式序列化。姓氏的稳定身份、带命名空间的扩展类型和条件输入由中文名保存。原版适配器在一次请求内准备临时卡片数据，复用原版的条件、分支及修饰逻辑，只把关联词库的取词交给现有加权取词器。预览和生成调用同一适配器。适配器隔离原版随机状态，并在结束时恢复。底层仍按生成结果执行校验和回退，并显示使用的规则与词库来源。要使用中文名姓氏继承的人名规则必须含有且只含有一个姓氏部件，出生时确定的完整姓氏供该部件直接使用。原版卡片里未设为姓氏的词组按原有语义运行。

源码依据见[原版编辑器](../../../Cultiway/.GameSource/Assets/Scripts/Assembly-CSharp/OnomasticsTab.cs)、[原版命名学数据及序列化](../../../Cultiway/.GameSource/Assets/Scripts/Assembly-CSharp/OnomasticsData.cs)和[原版命名入口](../../../Cultiway/.GameSource/Assets/Scripts/Assembly-CSharp/NameGenerator.cs)。

## 文化分化

跟随游戏真实的文化分化事件。原版已经通过 `Culture.cloneAndEvolveOnomastics` 复制母文化的卡片并对部分词组做拼写替换。原版卡片继续读取这一事件产生的子文化数据。中文规则也在这个事件里传承，继承的是规则引用、文化绑定、组用途和已应用的玩家修改。文化分化完成后，新文化独立保存自己的选择和修改。

中文名从命名包为该类型预先声明的变体中选择一项小变化，例如已有两种给名结构的文化开始偏好另一种，或城市开始使用同一包里的另一种行政后缀。候选变体按新文化的有效规则校验，适用时在这次分化选择，结果保存为规则和变体 ID。父文化先前的演化选择可以继续继承。已经被玩家设置过的字段、姓氏继承习惯及已继承的姓氏都会保留，候选只改动未被手动固定的字段。当前包没有可用变体时沿用继承的规则。原版词组的拼写替换与中文结构变体各作用于自己的数据。

同一文化的普通迁移、改名、改语言或读档不会触发分化。角色改变文化后，后续命名事件按当次请求适用的文化读取规则。已经有名字的对象继续保存已有名字。

源码事件见[文化分化调用](../../../Cultiway/.GameSource/Assets/Scripts/Assembly-CSharp/PlotsLibrary.cs)和[原版词组演化](../../../Cultiway/.GameSource/Assets/Scripts/Assembly-CSharp/OnomasticsEvolver.cs)。

## 语言怎样形成词库

规则里的「地名用字」「人名用字」「法术结尾」是用途。语言可以给每个用途绑定一个词库，也能限定到包里声明的子词库。命名包作者可以提供相关词群，如「水系地名」和「山地地名」。没有母语的新语言按世界的语言默认方案和创始者的物种选择初始词库与词群偏好。有明确来源的语言在真正分化时继承母语的词库引用和已应用调整，并从包允许变动的用途中选择少量词群偏好。两种语言可以拥有不同的候选词，也可以从相同的词库中以不同概率取词。默认包先为人名和地名提供词群，让玩家用内置内容就能体验分化。

分化只从包提供的词群和词条中选。演化结果按稳定 ID 保存在子语言上，每次生成直接读取它。母语后来编辑、消失或被重新载入都不影响这个记录。自动形成的用词差异通过同一个校验保证常用的必需用途仍有候选。玩家在语言页加入的词、排除、指定子库和手动倍率最终生效。缺失引用时在当前语言基础词库、该用途的默认来源或原版组保留的词中按规则回退。玩家排除贯穿回退路径。有效候选仍为空时，该规则按已有失败机制处理，预览显示缺词的用途和来源。

例如同一文化用「地名用字＋府」。一支语言保留水系词群，另一支分化后偏好山地用词，可能分别生成「澄江府」和「栖岭府」。这时沿用的「府」由文化决定。若文化自己分化选中了「地名用字＋州」，两种语言在该新文化里都按新的结构命名。词库差别体现在新生成的名字及其分布上。

游戏里新建语言的调用也用于初始化语言，因此只在明确的分化路径传入母语，并在创始者改加入之前建立子语言的命名方案。新语言本身的名字仍用创建者当时的文化与语言。先创建后分化的文化对象也按同样的顺序处理。

## 装卸、存档和扩展

- 原版世界中已有的卡片规则按原样读取，来源以打开编辑器前读到的存档记录为准。现有中文名 v1 世界继续使用原先的有效规则，并导入已经保存的文化、语言、启用包和字段修改。迁移后的语言先保留原有偏好，后续分化再按新方案形成词群。界面草稿带入草稿，应用状态由存档确定。两种世界里的已有名字和姓氏都由原对象保存。
- 新设定只保存引用、玩家修改和已产生的演化差异。命名包更换后，未固定的字段使用当前启用的内容。缺失的修改和演化引用标出来源并保留，重新启用兼容包时恢复。读档只恢复状态，预览不创建词库或推进演化。
- `NameRequest` 与 `NameResult` 继续用于其他模组接入。模组提供类型、输入和默认规则。用词用途沿用命名包与词库 ID，额外的词群和演化变体属于可选内容。Cultiway 有创法者的法术继续传该角色的文化与语言，共享法术继续用世界默认设置。法术与东方人族规则都由文化的「命名学」访问。
- 没有可用文化或语言时，按该命名类型和物种回落到相应的世界默认方案。已有的各类命名入口保留自己的来源约定和失败回退。

## 实施顺序与验收

| 阶段 | 交付和独立游戏验收 |
| --- | --- |
| 1. 命名学入口、预览和真实生成 | 先走通人名与城市。通过文化档案打开命名学，改一条卡片规则以及一个语言绑定，比较预览与实际生成并读档复核。验证中文规则也从这页修改，且继承「欧阳」时完整保留。验证原版卡片预览不会改变世界随机状态。 |
| 2. 文化与语言分化 | 用游戏的原版分化事件产生子文化与子语言。使用已知变体的测试包，检查父母方案、子对象各自变化的字段和词库来源，以及读档稳定性。再用相同结构和不同语言核对候选或取词分布，切包后确认已生成的名字仍在。 |
| 3. 其余入口与外部模组 | 扩展到已有的原版类型。安装 Cultiway 验证东方人族、带创法者的法术和世界共享法术。用现行存档、原版存档以及卸包再安装验证迁移与缺失引用恢复，在 720×480、1280×720 和 1600×900 实际检查鼠标和键盘操作。 |

这是设计方案。表中是实现后的验收条件，当前源码和已验证行为以[实现与验证](实现与验证.md)为准。
