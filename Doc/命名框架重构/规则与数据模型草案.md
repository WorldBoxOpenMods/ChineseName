## 核心数据及归属

| 数据 | 主要内容 | 归属 |
| --- | --- | --- |
| 命名类型定义 | 稳定类型 ID、显示信息、输入声明、可用扩展、预览与校验要求。 | 原版接入或注册类型的模组。 |
| 规则及规则方案 | 使用条件、权重、部件定义、排列顺序，以及类型到规则的绑定。 | 命名包提供默认内容，文化保存选择和玩家修改。 |
| 词汇用途与词库 | 用途标识、词条标识、文字、基础权重及可选标签。 | 命名包或玩家新增内容。 |
| 语言配置 | 各用途的词库来源、稳定偏好所需信息、词条排除和子词库限制。 | 语言在世界中的配置。 |
| 世界方案 | 当前启用包、优先级、默认绑定和世界级修改。 | 世界存档。 |
| 字段覆盖 | 对稳定目标的字段修改、新增内容、禁用状态和失效引用。 | 对应世界、文化或语言。 |
| 命名请求 | 类型、文化与语言信息、随机种子、已确定的名字部件和本次输入。 | 单次调用，生成时只读。 |
| 命名结果 | 成功或失败、名字、组成部分、所用规则与诊断信息。 | 单次调用，接入方决定写回。 |

这些是职责和数据记录，具体类与公开接口在实现方案中确定。框架保留通用能力，Cultiway 等模组负责把自己的对象转换为类型声明所需的信息。

命名请求中的文化与语言由接入方按已确认的对象来源规则选择，再提供给配置解析与执行。生成器不自行遍历游戏世界查找作者、所有者或亲代；已确定的姓氏与本次选用的文化、语言分别传入。

## 稳定标识

命名类型、规则、词汇用途、词库和可独立引用的词条，建议使用带命名空间的稳定 ID。显示名称、文件路径和代码属性名可以改变，持久化引用仍指向原 ID。

规则内的部件拥有局部稳定标识。规则 ID 和部件 ID 一起定位组成部分；移动部件保留 ID。复制或新增部件分配新的 ID。

示例中的 `base:person.two_given_chars`、`worldbox:unit` 和 `cultiway:spell` 用于说明模型，最终命名约定尚未定稿。

## 规则定义与顺序

建议将部件定义和排列顺序分别保存。下面是一条双字姓名规则的候选 JSON：

```json
{
  "id": "base:person.two_given_chars",
  "name_type": "worldbox:unit",
  "when": {
    "op": "eq",
    "field": "uses_surname",
    "value": true
  },
  "weight": 4,
  "parts": {
    "surname": {
      "op": "fixed_part",
      "key": "family_name"
    },
    "given_1": {
      "op": "word",
      "role": "base:given_character"
    },
    "given_2": {
      "op": "word",
      "role": "base:given_character"
    }
  },
  "order": ["surname", "given_1", "given_2"]
}
```

`parts` 按部件 ID 保存定义，`order` 只保存这些 ID 的顺序。编辑器拖动部件时修改顺序，调整某个部件的词汇用途时修改对应字段。

一条命名规则仍属于一个命名类型。物种、性别、身份等差异通过条件筛选；符合条件的规则按权重选择。

上述姓名示例中的 `fixed_part` 读取已经确定的姓氏。姓氏来源和继承选择在独立的继承流程中处理，部件执行不自行改写单位数据。

## 条件与组成部件

### 条件

条件建议采用结构化表达式，支持字段比较、集合包含，以及“全部满足”“任意满足”“不满足”等组合。条件字段由命名类型或扩展声明，编辑器据此提供适当控件。

例如，法术规则可以比较声明的 `element` 字段：

```json
{
  "op": "eq",
  "field": "element",
  "value": "fire"
}
```

建议区分三种求值位置：

| 位置 | 可以读取的内容 | 用途 |
| --- | --- | --- |
| 规则选择 | 本次输入与已确定部件。 | 判断规则是否适用。 |
| 部件执行 | 本次输入、已确定部件及当前局部执行状态中的部件结果。 | 判断是否输出某部分或选择某个分支。 |
| 词条筛选 | 本次输入、允许引用的部件结果，以及候选词条的文字与标签。 | 挑选符合元素、形态等要求的词。 |

引用生成结果时使用明确的部件 ID 和作用域，并纳入依赖检查。这样既能根据已生成片段作检查，也能避免依赖执行顺序中的隐式变量。

未知字段、字段缺失和字段值为假需要分别处理。候选方案是让条件返回“成立”“不成立”“信息不足”；信息不足不因取反变成成立，显式的“字段存在”检查仍能处理可选输入。具体校验与组合求值规则在接口设计中确定。复杂语义判断由模组注册自定义条件，并声明可编辑参数。

### 组成部件

建议从以下基础能力组织部件：

| 能力 | 输入与结果 |
| --- | --- |
| 固定文字 | 输出配置中的文字或分隔符。 |
| 按用途取词 | 使用词汇用途、语言配置和筛选条件抽取词条。 |
| 引用输入 | 读取本次请求中的创建者、城名等已提供信息。 |
| 引用确定部件 | 读取姓氏等已经确定的名字部件，并保留其身份。 |
| 引用本次部件结果 | 使用同一次尝试中某部件已生成的结果，保留所选词条与来源。 |
| 顺序分组 | 将多个部件作为一组执行，便于处理带分隔符的可选内容。 |
| 分支选择 | 根据条件与权重选择一段组成结构，避免独立变化相互组合后产生大量顶层规则。 |
| 有限重复 | 按有界次数重复生成片段，例如名字使用一个或两个用字。 |
| 引用规则片段 | 复用另一段结构，仅生成片段，检查依赖和调用深度。 |
| 文字变换 | 使用已注册操作对片段作截取、翻转等处理，并保留来源关系。 |
| 自定义部件 | 由其他模组提供实现、参数声明和预览支持。 |

必需或可选、启用状态和适用条件建议作为部件的通用属性。适用条件不成立表示本次不使用该部分；适用条件成立后缺少必需信息才使当前规则失败。条件依赖的信息缺失和条件明确为假需要区别处理。

可选组应整体成功或整体省略。例如“分隔点＋中缀”作为一组，中缀取词失败时连同分隔点省略，避免输出悬空标点。失败分支的临时结果不带入后续分支。

重复必须有上限。片段引用循环、过深调用和无效参数在校验及运行时受限；嵌套部件共同受单次命名的执行预算约束，避免各层独立重试放大执行次数。

已确定的继承姓氏保持原样，普通取词或文字变换不隐式重取或改写它。具体保护方式与片段结果结构一起设计。

基础部件的最终数量、分组和参数结构仍需细化。实现应将各部件的校验与执行分别组织，编辑器通过注册信息操作同一套数据。

### 复用结果与重新生成

“引用本次部件结果”和“引用规则片段”需要区分。例如，前一个部件已经抽到“炎”，引用其结果应继续得到“炎”；重新执行取词片段则可以抽到“焰”。

建议每次尝试保存局部部件结果，引用同一部件时读取同一份结果。调用可复用片段时创建独立的局部执行状态，避免多个调用相互覆盖。循环引用由依赖检查和运行时限制处理。

部件定义可以作为引用目标，输出顺序决定哪些部件直接出现在名字中。仅被其他部件引用的定义不需要额外输出，编辑器需要区分“直接输出”“被引用”和“未使用”的状态。确切 JSON 表示仍待细化。

### 模组扩展与统一取词

自定义部件建议返回可追踪的片段结果，而非直接修改待命名对象。需要按词汇用途取词时复用统一取词服务，使语言偏好、排除和来源追踪继续生效。

模组也可以提供动态候选来源，交出候选标识、文字、权重及标签，由统一取词流程筛选和抽取。动态候选来源的具体接口与生命周期需要在扩展接口设计中细化。

## 词汇用途与语言

规则引用 `base:given_character` 这类用途，语言配置再将用途连接到实际词库。直接指定词库的能力保留，其适用方式仍需细化。

词库记录的候选形式如下：

```json
{
  "id": "base:given_characters",
  "entries": {
    "base:given.qing": {
      "text": "青",
      "weight": 1,
      "tags": []
    },
    "base:given.chuan": {
      "text": "川",
      "weight": 1,
      "tags": []
    }
  }
}
```

语言配置中的用途绑定可以表达为：

```json
{
  "role_bindings": {
    "base:given_character": [
      {
        "library": "base:given_characters",
        "weight_multiplier": 1
      }
    ]
  },
  "preference_seed": 1234
}
```

上述种子只用于展示存储需求，不规定具体算法。候选方案是在用途、标签、排除项和子词库筛选之后，用词条基础权重、词库绑定倍率和语言的稳定偏好共同决定抽取倾向。示例使用 `weight_multiplier` 明确它是倍率，其最终字段名仍待定。

默认语言偏好应保留候选的可达性，显式排除和子词库限制单独处理。偏好不改写命名包里的原始权重。稳定算法、差异幅度与新增词条的偏好仍需具体设计；重复词条行为按下面的已确认规则处理。

### 词条身份与重复引用

已确认同一词条的重复引用只计算一次、采用最高有效来源倍率，同字异义词条保留并分组展示；玩家可按文字或指定词条排除。多包同字段修改按优先级处理，同级不同值报冲突；缺少模组只影响相关内容，导出修改默认形成声明依赖的补充包。以下字段名、引用表示及更细的冲突校验算法仍为技术草案。

建议区分“定义一条词”和“把已有词加入某词库”：一条稳定词条 ID 在同一有效配置中只有一份定义，可以由多个词库引用。重复引用不增加候选份数；重新定义同 ID 必须使用明确的替换操作。

现有 `entries` 示例可以继续表达本词库定义并包含的词，另以引用字段包含已有词，例如：

```json
{
  "id": "landscape:given_characters",
  "entry_refs": ["base:given.qing"],
  "entries": {
    "landscape:given.lan": {
      "text": "岚",
      "weight": 1,
      "tags": ["nature"]
    }
  }
}
```

`entry_refs` 只是候选字段名。它不重新定义“青”的文字、标签或基础权重，也不把词条永久追加进别的包的原始列表。

相同文字但不同 ID 不自动合并。比如“青”分别表达颜色与草木意象时，可能拥有不同标签和使用条件；筛选后它们仍是不同候选。不能把两份标签合并后让某个词获得原本没有的含义。若两个独立 ID 同时符合条件，它们的概率都会计入最终显示为“青”的总概率，界面应提示同字来源。

作者调整已有词库时，同一词义优先引用原词条并显式覆盖需要修改的字段；新增另一含义再使用独立 ID。这样能保留编辑与依赖的对应关系，也避免将整份词库复制成新 ID 后无意增加全部同字的概率。

词库编辑器按显示文字分组，展开后查看各词条的 ID、含义、标签和来源。普通操作可以排除当前语言、当前用途下全部同字词条；精细操作可只排除指定 ID。按 ID 保存的排除不会自动转移给后来出现的另一个 ID，按文字保存的排除则继续匹配之后加入的同字内容。

### 多来源权重

按已确认的最高来源倍率，在一次具体用途的取词中先确定有效词条与适用的来源路径，再计算：

```text
词条有效权重 = 最终词条基础权重 × 最大有效来源倍率 × 语言偏好系数
抽取概率 = 该词条有效权重 / 全部有效候选的权重之和
```

“最终基础权重”已经包含明确替换与玩家对应字段覆盖；语言偏好系数包含该语言的稳定偏好及手工偏好调整。同一个字段不会在覆盖后再额外加算一次。各来源倍率在筛选当前用途、条件和排除之后取最大值，不相加。

例如所有词条基础权重与语言偏好系数均为 1：

| 词库绑定 | 包含的词条 | 权重倍率 |
| --- | --- | --- |
| 通用名字用字 | 青、川 | 1 |
| 山水名字用字 | 引用同一条青，另含岚 | 3 |

得到以下候选：

| 词条 | 有效权重 | 概率 |
| --- | --- | --- |
| 青 | `1 × max(1, 3) × 1 = 3` | `3/7` |
| 川 | `1 × 1 × 1 = 1` | `1/7` |
| 岚 | `1 × 3 × 1 = 3` | `3/7` |

重复引用同一条青，不会把它的权重变成 4；调高山水绑定的倍率，仍能增强其适用词汇。把青的语言偏好系数改为 2 后，三者权重为 6、1、3，概率分别为 60%、10%、30%。排除青后，川与岚的概率分别为 25% 和 75%。

倍率不是词库的总概率份额。一个包含很多有效词条的词库，总贡献通常更大，编辑器应显示候选数量和合成权重，不把倍率标成“某词库占比”。如果以后需要严格按词库份额抽取，应作为另一个明确策略设计，不能与当前公式混用。

### 排除、零权重与直接指定词库

先执行用途、标签、条件、子词库及显式排除，再对剩余路径与词条计算权重。玩家明确排除的词条不会被其他包的较高权重重新启用；候选为空时规则失败或明确的可选组省略，继续既定回退，不悄悄清空排除项。

词条基础权重为 0 表示该词条当前不参与抽取；某个词库绑定倍率为 0 只关闭该来源路径，若同一词条仍有其他有效来源则可继续参与。负数或非有限数值是配置错误，不能静默转换为正常权重。数值范围与计算中的归一化实现，在接口定稿时确定。

直接指定词库的部件继续使用同一套筛选、排除、偏好与抽取流程，来源集合换为指定的词库，视为本次取词的显式来源，默认倍率为 1，不额外计入未参与的语言词库绑定。词库及依赖仍须在当前范围可用。若没有语言对象，则使用适用的默认语言配置，不让直接取词形成一条绕过玩家限制的执行路径。

语言在正常使用中保持稳定；新语言有来源时继承方案并形成相近的偏好。玩家修改和包更新按已确认行为生效。

## 包内容与玩家覆盖

建议分别为文化规则和语言词汇计算有效配置，保留二者的职责边界。各自按以下顺序组合：

1. 读取当前绑定的基础方案。
2. 按配置范围和玩家设定的包优先级，执行追加、替换和排除操作。
3. 应用对应世界、文化或语言的玩家字段覆盖。
4. 校验有效内容，记录来源和不可用项，供生成与预览使用。

### 范围、优先级与操作

包文件和定义可以全局共享，合并结果按当前世界、所选文化或语言方案及命名用途计算。未启用、未绑定或不适用的内容不进入本次合并，同一份原始内容不能被某个世界的替换操作原地修改。

建议在每个具体绑定中使用一个基础方案，再叠加适用的补充操作。多个包提供基础方案时，由绑定选择使用哪一个，不因为安装数量增加就自动混合全部内容。默认匹配条件的具体排序继续在初始化方案中确定。

补充操作从低优先级到高优先级执行，再应用玩家覆盖；同一包内按明确的操作顺序处理。界面用可拖动顺序表达包的先后，保存稳定标识；不能依赖目录扫描、文件名或模组加载时间决定结果。

| 操作 | 建议语义 |
| --- | --- |
| 追加 | 新增一个稳定标识的定义，或把已有定义的引用加入指定集合。重复加入同一引用是幂等操作，不复制候选。 |
| 替换 | 指明资源、稳定目标及字段，或明确替换整个定义；调整权重等局部字段时保留未涉及的内容。 |
| 排除 | 在指定范围抑制规则、词条或集合成员，保留其定义和来源，不物理删除其他包内容。 |

同一引用的追加与排除都可以表达集合成员的启用状态，明确较高优先级的操作决定该范围内的最终状态。替换词条权重不等于重新启用已经排除的集合成员；需要恢复成员时必须明确包含它。玩家的禁用或排除最后生效，包操作不能越过它。

字典条目与集合成员按稳定 ID 操作，移动条目不改变目标。输出顺序作为独立字段处理；标签与排除集合用成员增减表达，不根据数组位置覆盖。整个定义的替换是明确操作，不自动把两个结构任意深度合并。

### 同级冲突与无效内容

同级主要用于处理导入配置或尚未指定顺序的包。建议采用以下规则：

| 情况 | 候选处理 |
| --- | --- |
| 不同优先级明确替换同一字段 | 较高优先级生效，保留完整来源链。 |
| 同级修改同一目标的不同字段 | 字段兼容且通过最终校验时可以同时生效。 |
| 同级把同一字段设置为相同值 | 值一致时不视为歧义，保留多个来源。 |
| 同级把同一字段设置为不同值 | 标记冲突，不按文件名选胜者；需要明确先后或由兼容的玩家覆盖给出该字段的最终值。 |
| 同级替换整个定义，同时修改它的内部字段 | 作为重叠写入检查冲突，不能假定自动合并。 |
| 追加定义时撞上已有 ID | 标记重复定义；改为引用已有词、明确替换，或为新内容使用独立 ID。优先级不能把追加自动解释为替换。 |
| 同级启用与排除同一集合成员 | 标记启用状态冲突，等待明确先后或玩家选择。 |

未解决的冲突只使相关定义、字段或规则不可用，其他独立内容继续工作。生成按既定路径尝试其他规则和回退，诊断明确指出受影响目标，不能把冲突伪装成正常采用了某个包。玩家覆盖只有实际给出冲突字段的兼容最终值时才解决该字段，调整无关权重不会修复部件类型冲突。

格式、参数或资源类型本身无效的内容单元不执行其中的部分操作，保留错误并标为不可用，避免出现前半部分补丁已写入、后半部分失败的状态。内容单元指清单明示的一组内容或操作，具体文件字段尚待定；不同独立单元可以分别校验。玩家草稿的应用继续遵守已经确认的结构、参数检查与保留旧生效配置的规则。

### 依赖与版本

建议把整个包共用的必需依赖和可选内容单元的依赖分开。比如同一包中的普通人名与 Cultiway 法术规则分别声明依赖，Cultiway 缺失时仅法术单元不可用，人名内容继续工作；相关世界编辑原样保留。

| 情况 | 候选处理 |
| --- | --- |
| 依赖包只安装、未在需要范围启用 | 不暗中启用；显示依赖与影响范围，玩家可以将启用依赖纳入当前配置草稿。 |
| 依赖在当前范围不可用 | 相关单元标记缺失并进入回退；不读取已关闭词库绕过启用设置。 |
| 必需依赖存在循环 | 报告依赖链，涉及循环的单元不可用，不影响无关内容。 |
| 优先级与依赖关系 | 依赖声明可用性要求，优先级决定合法写入的先后；优先级不能解决缺失或循环。 |
| 同一包 ID 出现多个不同版本的目录 | 提示选择当前安装版本，不按扫描顺序自动选取；正常更新作为明确的包替换操作。 |

当前安装版本仍全局共享，世界保存引用、启用与修改，读档不回滚包版本。版本范围、可选内容单元和依赖标识的精确 JSON 写法继续在调用协议中定稿。

### 编辑导出

玩家把词库和规则修改导出时，默认生成包含新增内容与明确覆盖操作的补充包，保留目标 ID 并声明所需基础包；不自动复制整库并重建所有 ID。独立完整方案作为另一个明确的制作方式，在导出前检查所用定义与依赖是否齐全。两种形式都使用同一个包模型，不要求分发框架代码。

### 玩家字段覆盖

字段覆盖使用稳定目标 ID、字段路径和修改值，避免依赖列表位置。例如，修改上文姓名规则的第一个名字部件用途，可以定位为：

```json
{
  "target": "base:person.two_given_chars",
  "path": ["parts", "given_1", "role"],
  "value": "my_pack:preferred_given_character"
}
```

新增规则与词条、禁用状态分别保存。包移除目标时，覆盖记录保留并显示缺失，不自动绑定到同位置的其他条目。

### 字段与条目的合并场景

建议按以下方式细化已经确定的字段覆盖行为：

| 场景 | 候选处理方式 |
| --- | --- |
| 玩家把权重改为 8，包把默认权重改为 6 | 玩家权重仍为 8，显示默认值与覆盖值的来源。 |
| 玩家只改一个取词部件的用途，包更新其他参数 | 保留该用途，其他兼容且未修改的字段跟随更新。 |
| 玩家只改部件顺序，包更新部件参数 | 保留顺序，兼容且未修改的部件参数继续更新。 |
| 玩家禁用默认规则，包修改该规则 | 保留禁用状态，重置后可以恢复当前默认内容。 |
| 包移除玩家正在使用的规则或部件 | 保留相关编辑并标记缺失，受影响规则按既定失败与回退方式处理。 |
| 包改变部件类型，旧覆盖包含不再适用的参数 | 标记结构冲突，保留原覆盖供修复，不把旧参数静默套给新类型。 |
| 包以追加操作重复定义已有 ID | 标记内容冲突，要求使用显式替换操作或独立 ID，不依赖加载先后覆盖。 |

包操作按当前启用配置重新组合，不将每次操作永久追加到共享列表。禁用补充包后，对应贡献撤去，基础内容和其他有效覆盖继续参与计算。

### 新增部件与玩家顺序

`order` 作为独立字段覆盖的候选结构继续保留，部件设置分别更新。包新增输出部件的产品行为已经确认。

例如，基础方案是“姓氏→名字”，玩家改成“名字→姓氏”；包更新后，默认方案变为“称号→姓氏→名字”。采用以下处理：

1. 已经自定义顺序的规则仍输出“名字→姓氏”，新增“称号”标为“待加入”，由玩家选择是否采用。
2. 未修改顺序的规则自动采用新的默认顺序“称号→姓氏→名字”。
3. 已有部件中未修改的设置继续跟随包更新，待加入状态不冻结这些更新。

“待加入”针对新增到默认输出顺序的部件，不等同于全局禁用其定义。仅作为其他部件依赖的定义，仍按引用与依赖规则处理。具体提示、插入位置选择和缺失部件修复交互仍需设计。

### 删除与部件类型变更

建议按是否影响当前使用的内容处理：

| 情况 | 候选处理方式 |
| --- | --- |
| 包移除未使用的定义 | 显示相关编辑失去目标，不因未使用内容失效而阻断其他生成。 |
| 包移除当前使用的必需部件 | 受影响规则不可用，保留自定义顺序和字段覆盖，按既定路径尝试其他规则或回退。 |
| 明确可选的组存在缺失依赖 | 按可选组整体省略的规则处理，保留问题与来源信息。 |
| 同 ID 部件类型改变，旧字段覆盖不再适用 | 标记类型或参数冲突，保留编辑，不根据字段位置猜测新的对应关系。 |

修复入口可以提供重置受影响字段、重新绑定兼容目标或保存为独立规则。具体操作仍需和编辑器一起评审。

命名包文件全局共享，世界保存启用配置、绑定和玩家修改。包内容使用当前安装版本，不在每个世界复制完整原始包。

## 请求与结果

### 请求

命名请求建议包含类型 ID、所用文化和语言、种子、类型声明的输入，以及已经确定的名字部件。原版生物和其他模组对象由各自接入方准备请求，框架不要求对象都是 `Actor`。

输入在本次生成中保持只读。预览使用模拟输入或实际对象信息副本，避免读取对象的行为顺带触发真实命名或继承写入。

### 结果

结果明确表示成功或失败，成功时包含文本与组成部分。诊断需要能够关联规则、部件和内容来源；详细追踪可以按预览与排错需要提供，具体存储方式待定。

接入方在成功后将结果写回对象。姓氏等长期信息由对应流程保存，失败尝试和预览不提交半成品。

## 生成与编辑流程

生成时先取得当前有效配置，再筛选条件成立的规则，按权重选择并执行组成部件。候选接受类型对应的长度、重名等校验；失败后在限制内重试，之后依次使用类型默认方案与接入方回退。

执行状态与规则定义分开，重试不修改共享规则或原始词库。每次尝试的临时值独立，保留已经确定的姓氏等输入。随机计算需要与游戏其他随机状态隔离，使预览不影响世界运行。

编辑器操作草稿，预览执行草稿对应的有效模型。应用时检查结构与参数，再更新生效配置。缺失包或扩展按已确认的标记和回退方式处理，原有修改保留。

## 三个案例

### 人名与姓氏继承

孩子采用优先父姓文化，父亲已经有姓“李”。继承流程先确定孩子的姓氏，接入方将 `family_name` 作为确定部件提供。随后规则按孩子的语言抽取名字用字。

已确认出生时确定并保存姓氏，首次需要姓名时生成完整名字；两步不要求在同一次游戏调用中完成。克隆复制原姓名、姓氏及组成部分，亡灵转换与升格保留个人姓名。

继承只选择一位亲代的完整姓氏，`family_name` 作为整体保存和传递，不拆分或拼接双方姓氏。例如亲代姓“欧阳”时，继承结果仍为“欧阳”。

一项可能的结果为“李青川”：姓氏来自确定部件，“青”和“川”来自语言绑定的名字词库。结果同时保留各组成部分。预览使用模拟姓氏，真实生成成功后由接入方写回姓名。

父亲使用姓氏但尚未初始化时，继承流程先确定并保存父亲姓氏。已有姓氏不因包切换或语言改变而重新抽取。

### Cultiway 法术命名

Cultiway 注册法术类型、元素与形态输入、词汇用途和预览信息。实际请求提供火属性、剑形态以及相关文化、语言。

文化规则配置“元素修饰、形态词、术法后缀”，由框架或模组部件按输入筛选候选。语言提供“炎”“刃”“诀”等词，得到“炎刃诀”这类结果，Cultiway 再将结果写回自己的法术对象。

更复杂的功法意象可以由模组部件提供，玩家仍能把部件放进可编辑的文化结构中。

### 包更新与切换

玩家把双字姓名规则的权重从 4 改成 8，仅保存 `weight` 覆盖。命名包更新词库和未修改部件参数时，这些内容继续更新，权重仍为 8。

玩家切换词库方案后，应用配置，新名字使用新的有效内容。已有姓名保留，既有姓氏继续作为确定部件传入。

原规则被移除时，修改记录保留并标记缺失。生成进入可用规则与既定回退路径，玩家可以修复绑定或重新启用对应包。

## 评审重点

1. 已确认新增输出部件等待玩家选择后，具体怎样提示、选择插入位置和恢复默认顺序。
2. 基础部件、通用属性、局部结果引用与片段复用的划分是否完整。
3. 按已确认的词条身份、最大来源倍率、排除、同级冲突与依赖隔离行为，落实字段、集合操作与校验算法。
4. 部件移除、类型改变与玩家覆盖冲突时，怎样呈现和修复。
5. 输入、确定部件和结果是否足以支撑姓氏继承、原版入口与 Cultiway 接入。
6. 默认方案选择、稳定偏好、依赖校验和存档如何落实为具体接口。

评审后再将定稿部分拆为实现阶段、接口约定、原版覆盖清单和测试场景。
